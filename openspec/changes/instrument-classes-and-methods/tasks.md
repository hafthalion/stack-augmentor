# Tasks

## 1. Runtime: configuration model

- [x] 1.1 `IdSpec`: add `Annotations`, and move `memberName()` to `FieldSpec`/`MethodSpec`. `ParamRef`: add `Annotations`, parsed from the `[instrument.methods]` value `"@"` (and rejected inside arrays). `AugmentorConfig`: rename `ids`/`params` to `classes`/`methods` (fields, accessors, `Builder`, `equals`/`hashCode`/`toString`), rename `hasParamEntries` to `hasMethodEntries`, remove `annotatedClasses` and `honoursAnnotations`, and add `hasInstrumentEntries()`. `ConfigReader`: `INSTRUMENT_KEYS = ["classes", "methods"]`, class keys validated with `CLASS_PART`, and class values `"@"`, `name` or `name()`. Verify with `AugmentorConfigTest`: the full configuration uses the new tables; `annotatedClasses`, `classIds` and `methodParams` are rejected as unknown keys naming `classes, methods`; `"@id"` and `"com.acme.Ord+er"` are rejected with the key and line; a methods value `"@"` parses to `ParamRef.Annotations`, and `["@"]` is rejected.
- [x] 1.2 Add `ClassEntry(key, spec)` with `isPattern()`, and `classEntry(className)`: exact entry first, then the precompiled patterns sorted by specificity (literal characters descending, then key). Verify with `AugmentorConfigTest`: exact beats pattern, a longer pattern beats a shorter one (`"com.acme.legacy.*"` vs `"com.acme.**"`), a tie is decided by key order, `"**"` matches everything, and no match gives `null`.

## 2. Runtime: id resolution and handler

- [x] 2.1 `IdResolver`: take `annotationsWithoutEntry`, and walk the superclass chain for the deciding entry: explicit entries go through `sourceFor(owner, spec)`, `Annotations` through the annotation search from `owner`, and no entry gives the fallback or `null`. A missing member warns only for exact entries, and is a debug message for patterns. Verify with `IdResolverTest` (helper rebuilt on `classes`): no `"@"` entry means no annotated receiver id; an `"@"` entry works; a superclass entry applies to subclasses; most-specific-wins (an explicit exact entry beats a `"@"` pattern); a pattern with a missing member prints no `WARN` (capture `System.err`); fallback mode uses annotations without an entry.
- [x] 2.2 `ThrowHandler`: the no-argument constructor passes `annotationsWithoutEntry = true`, and `ThrowHandler(AugmentorConfig)` passes `false`. Verify with a new `ThrowHandlerTest` (Kotlin, runtime module, no classpath configuration): `onThrow` for an annotated receiver rewrites the frame with its id.

## 3. Instrument: deciding entries

Use it in `TypeMatching` (`receiverRelevant`, the `describe` reasons) and in `IdParameters.select`: parameter annotations are used when the deciding entry is `Annotations` or `paramRefs` contains `ParamRef.Annotations`, and the ref loop skips `ParamRef.Annotations`. Make the "ignoring" debug message per member, naming `[instrument.classes]` and `[instrument.methods]` (design decision 2). Verify with `ParameterSelectionTest`, switched to `"@"` entries: annotations ignored without an `"@"` entry; an explicit exact entry disabling a class's `@StackTraceParam`; a `[instrument.methods]` `"@"` entry re-enabling `@StackTraceParam` and a class-level `@StackTraceParams` for the matched method only; the per-member "ignoring" message; wildcard `[instrument.methods]` behaviour unchanged.
